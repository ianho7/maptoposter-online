# 为什么水体渲染问题反复出现：一次从“补画蓝色”到“重建海陆判断”的复盘


> 结论先说：在**不更换 OSM / Overpass 数据源**这一约束下，这次 V2 已经修复了此前反复出现的那一类共同工程根因——高密度、局部不规则的海岸线数据进入一个“固定数量上限 + 点位猜测 + 任一异常全局放弃”的处理方式后，导致整片海面缺失或陆地被覆盖。
>
> 但这不是“今后所有水体数据都绝不会出错”的承诺。原始地图数据若严重缺失、海岸线方向整体错误或存在巨大断口，系统仍会选择保守地少画水，而不是冒险覆盖陆地。这是明确设计的安全边界，而非尚未发现的缺陷。

## 1. 这不是一张普通地图，而是一条从地理数据到海报的处理链

Map to Poster 是一个把 OpenStreetMap（以下简称 OSM）的地理数据转换为 PNG、SVG 海报的应用。用户输入一个城市，应用获取道路、水体、绿地等要素，再把它们组合为可打印的地图。

“水体显示正确”其实跨越了多道环节：

```text
OSM / Overpass 原始地理数据
        ↓
后台数据线程：裁切、缓存、补全外海
        ↓
水体多边形：湖泊、河流、海面与岛屿的边界
        ↓
WASM 绘制器：编码并绘制到画布
        ↓
PNG / SVG 导出
```

这里有一个容易被忽略的事实：OSM 通常把海岸线提供为**有方向的线**，而不是“海面多边形”。应用必须根据这些线推导出查询范围中哪一侧是海、哪一侧是陆地；与此同时，湖泊、河流、公园和岛屿又可能以完全不同的要素形式出现。

因此，屏幕上看似同样的“蓝色没有画出来”，背后可能是数据语义、几何计算、缓存版本、后台线程，或最终绘制环节中的任意一个问题。

## 2. 为什么会连续出现纽约、南京、海口和里斯本

这几次案例并非完全相同，但它们共同暴露了旧方案的假设不成立。

| 案例 | 看到的现象 | 当时真正碰到的问题 |
| --- | --- | --- |
| 纽约 | 曼哈顿一度被海面错误覆盖，之后又曾出现陆地要素消失 | 不能以海报中心或单一位置判断整个画面哪边是海 |
| 南京玄武湖 | 湖被误当成绿地；道路避让开关又让视觉结果产生差异；河中岛屿曾只剩轮廓 | 水体、绿地、岛屿必须保留各自的语义与内洞关系，不能只按绘制顺序“盖颜色” |
| 海口 | 北侧海面一度完全不见 | 除了算法本身，旧的后台线程或缓存结果也可能让已修复的代码看起来仍然失效 |
| 里斯本 | 左下角外海被当作背景色，像是陆地 | 高密度海岸线触发固定数量上限；即便勉强处理，局部点位判断的歧义也会让整批海面放弃生成 |

换句话说，前几个案例让我们逐渐知道“不能把海水画到陆地上”；里斯本则证明，仅仅避免误覆盖还不够，处理方法本身必须能承受真实世界中复杂、密集和不完全规整的海岸线。

## 3. 必须诚实反思：前几轮哪里做得不够好

### 3.1 把表现按城市拆开了，而没有先按失效模式归类

最初的排查很自然地围绕“纽约问题”“玄武湖问题”“海口问题”展开。这样能快速缓解眼前现象，但会让人误以为每座城市都需要一条特殊规则。

实际上，应该更早把问题分为四类：

1. 原始数据的语义是否正确，例如湖泊是不是被标成公园；
2. 海岸线能否生成可信的海陆区域；
3. 生成结果是否真的穿过缓存和后台线程抵达绘制器；
4. 最终海报是否与输入几何一致。

没有这个分层，就容易在后面的层修前面的病：通过调整画层顺序修数据语义，通过增加数量上限修几何判断，通过截图判断后台线程是否更新。它们都可能暂时“看起来好了”，却无法形成可迁移的解法。

### 3.2 过早把问题理解为“绘制顺序”

南京玄武湖提醒了我们：如果一个水体被数据提取阶段归为绿地，或者水面多边形丢了内洞，改变道路、绿地、水体的绘制顺序只能改变谁盖住谁，不能恢复正确的地理含义。

这也是河中岛屿曾出现“只有描边、没有实心”的原因：问题不在“岛屿颜色”本身，而在水面边界中的洞与陆地要素没有被完整保留。之后的修复把“湖泊、海面、岛屿、绿地”的含义分开处理，而不是让某一个图层承担所有纠错责任。

### 3.3 旧海面生成器依赖两个脆弱的经验规则

旧方案已经比“看海报中心点”进步：它利用 OSM 海岸线的方向——沿线前进时，右侧通常是水、左侧通常是陆地——来避免淹没纽约的多块陆地。

但实现仍有两个根本脆弱点：

- **固定数量上限**：裁切后的线段超过 6,000 条就直接放弃生成；
- **左右偏移采样**：在海岸线两侧各取一点，猜测这个点落在某个候选区域的哪边。

里斯本的实际输入有 549 条海岸线要素，裁切后达到 21,521 条线段，旧逻辑因此以 `processing-budget` 退出并返回零个海面。把上限提高并不是真正的方案：轻度简化后，仍有约 61 条局部线段无法用偏移点稳定对应到候选区域；旧逻辑把任意一次局部歧义视为整座城市都不可信，最终还是返回空结果。

这是前几轮最大的设计问题：**把局部异常升级成全局失败。**

### 3.4 安全原则是对的，失败语义却太粗

“不确定时不要覆盖陆地”是必须保留的原则。纽约案例表明，宁可少画外海，也不能让曼哈顿变成海。

问题在于旧代码把“保守”实现成了“只要有一个局部判断不出来，就不生成任何海面”。这会使一个港口、交叉点或数据碎片影响数十公里外本来可信的海域。安全不是全盘放弃；更好的安全语义应当是：**只拒绝证据冲突的那一个候选区域，其他被充分证明的区域继续输出。**

### 3.5 可观测性和验收闭环建立得太晚

海口曾出现“代码已改但画面仍不对”的困惑，后来确认开发服务仍在使用旧的后台线程产物；诊断导出开关又会主动请求原始水体数据，因此容易被误判为“水体没有缓存”。这些并不是海岸线算法错误，却会极大干扰判断。

早期我们缺少三样东西：

- 能从后台线程传回界面的阶段日志；
- 能离线重放的最小真实海岸线样本；
- 把“单元测试通过”和“真实 PNG/SVG 导出正确”分开的验收门禁。

结果是视觉观察、缓存状态和代码版本曾混在一起讨论，排查过程自然容易反复。问题不只是少写了几条日志，而是缺少一条可重复、可证伪的证据链。

## 4. 这次找到的共同根因是什么

里斯本把共同根因暴露得最清楚：旧系统假设“海岸线是数量可控、每一段都可被点位采样稳定解释的数据”。真实 OSM 数据并不保证这一点。

高密度海岸线会超过固定预算；海岸线相交、贴边、被裁切或关系要素展开后，微小的偏移点可能落到边界上或错误的相邻区域；最后，旧实现又将一次局部失败放大为全局空结果。

因此，根因不是某一城市的海水颜色，也不单是一个阈值。它是：

> **系统用局部坐标猜测来回答一个本应由边界关系回答的问题，并且没有把计算成本约束到实际输出分辨率。**

这也解释了为什么此前的症状会“陆续出现”：纽约先触及了多陆地判断，南京触及了水体与岛屿语义，海口揭示了运行版本与结果链路，里斯本最终触及了复杂海岸线的规模与拓扑边界。它们逐层暴露的是同一条处理链不够稳健的不同断面。

## 5. V2 怎样改变问题结构，而不只是再加一个补丁

V2 保持 OSM / Overpass 数据源、既有 Water GeoJSON 输出和 WASM 绘制接口不变，但替换了“补外海”的核心判断方式。

### 5.1 先按海报能看见的精度压缩数据

海报不会因为海岸线在亚米级多一个折点而更清晰。V2 先把经纬度转换到本地米制坐标，再使用保持连接关系的简化算法，把允许误差限定为画面最大边的 0.25 像素；必要时才上调到 0.5 像素。

它不是“随便删点”，而是先要求端点、闭合状态、方向和线之间的连接关系都保持一致。目标是把处理成本与海报分辨率关联，而不是与原始数据的采样密度硬绑定。

```ts
const simplified = simplifyMetricLinesForBudget(
  cleaned.lines,
  viewportBbox,
  projection,
  segmentBudgetOptions
);

if (simplified.exceededHardLimit || !simplified.structurePreserved) {
  return { polygons: [], diagnostics };
}
```

在里斯本的真实输入中，21,521 条裁切后线段被简化为 6,762 条，容差为 8.333 米；这仍低于该海报分辨率能辨认的误差，并把后续拓扑计算控制在可接受范围内。

### 5.2 不再在边上“取一点猜一猜”，而是直接比较区域与边的邻接关系

V2 把海岸线与查询范围边界一起切分，生成彼此不重叠的候选区域。随后，它记录每条切分后的海岸线来自哪个原始要素、原始方向是什么，并直接判断候选区域位于该边的左侧还是右侧。

这段核心逻辑不再创建偏移采样点：

```ts
const sameDirection = edge.forward === adjacentFace.forward;
const side = sameDirection ? adjacentFace.faceSide : oppositeSide(adjacentFace.faceSide);

evidence[adjacentFace.faceIndex][side === "right" ? "water" : "land"] += length;
```

意思是：沿着 OSM 海岸线的原始方向，位于右侧的候选区域累积“水侧证据”，位于左侧的区域累积“陆侧证据”。证据来自共享边的长度，而不是一个容易落到边界上的单点。

候选区域只有同时满足“触及查询边界、拥有足够水侧证据、没有陆侧证据、面积和几何都有效”时，才会被输出为海面。

### 5.3 把“一处异常，全部消失”改为“局部拒绝，可信部分保留”

新的判定逻辑对每个候选区域独立处理：水陆证据冲突，拒绝该区域；证据不足，拒绝该区域；其他区域不受影响。

```ts
if (faceEvidence.water > 0 && faceEvidence.land > METRIC_EPSILON) {
  diagnostics.rejectedConflictFaces++;
  continue;
}

if (faceEvidence.water < minimumSupport || !metricPolygonTouchesBoundary(face, bbox)) {
  diagnostics.rejectedInsufficientSupportFaces++;
  continue;
}
acceptedFaces.push(face);
```

这保留了纽约案例建立的安全底线：数据不确定时不把陆地涂成海；同时移除了旧方案不必要的连坐机制。

### 5.4 让“我到底跑的是哪一版”可被验证

V2 同时升级缓存版本为 `v12-coastline-topology-v2`，并让后台数据线程把每次水体处理的汇总日志回传给界面。日志记录裁切、简化、切分与区域生成耗时，以及输入线段、简化后线段、匹配与未匹配边、接受和拒绝区域数量。

```ts
const line = `[Timing][${scope}][${name}] ${parts.join(" ")}`;
console.log(line);
sendDiagnosticLog(line);
```

这一步不能直接让海面变蓝，却让“代码没生效”“旧缓存命中”“数据真的异常”成为可区分、可复查的三种结论。

## 6. 我们如何验证它不是只修好了里斯本

验证不能只看单元测试，也不能只看一张截图。因此本次建立了四层证据。

| 验证层 | 证据 | 证明的内容 |
| --- | --- | --- |
| 最小真实回归 | 提取 549 条里斯本海岸线作为约 0.8 MB 的离线样本 | 密集真实输入可重复测试，不依赖网络与浏览器 |
| 算法性质测试 | 方向、岛屿/内洞、输入顺序、线条加密、局部无法匹配边 | 新算法不会因常见的几何扰动倒退为旧问题 |
| 数据链路回放 | 原始水体数据、诊断日志、缓存版本和二进制水体输出 | 新生成器确实被数据线程调用，结果进入绘制输入 |
| 最终导出 | 里斯本 PNG 与 SVG，及纽约、海口、南京真实海报 | 用户最终看到的 PNG/SVG 与正确水体几何一致 |

最终回归结果如下：

| 城市 | 本轮重点 | 结果 |
| --- | --- | --- |
| 里斯本 | 西南外海、密集海岸线、PNG/SVG 一致性 | 外海恢复；PNG 与 SVG 的 185,592 个水体坐标对比，最大偏差 0.051 像素 |
| 纽约 | 曼哈顿、多块陆地不被覆盖 | 水道保持为水，曼哈顿、布鲁克林、泽西市等采样陆地点未落入生成海面 |
| 海口 | 北侧海面 | 海面存在；当前数据链日志无冲突或未匹配区域导致的全局降级 |
| 南京 | 玄武湖、岛屿/内洞、道路避让开关 | 显式湖泊及其内洞保留；开关开/关均进入同一水体几何，未改变玄武湖的水体语义 |

自动验证方面，水体与海岸线相关测试共 34 项通过，类型检查和生产构建通过。更重要的是，清单把“离线验证通过”与“真实导出通过”分为不同门禁；只有最后一层也闭合后，V2 才被标记为完成。

## 7. 所以，这次算不算“从根本上修复”？

答案需要分范围说。

| 判断 | 结论 | 原因 |
| --- | --- | --- |
| 是否修复了此前反复出现的共同工程根因？ | **是** | 固定阈值、偏移点猜测、局部异常全局失败已被分辨率约束、边界邻接判断和区域级拒绝替代 |
| 是否在既定数据源下是最合适的方案？ | **是，在当前约束内** | 它利用已有海岸线方向与几何关系，不增加全球数据源，也不把风险转嫁给绘制层 |
| 是否保证世界任何地点永远正确？ | **否** | 上游数据可缺失、方向可错误、海岸线可存在巨大断口；没有额外权威海陆面数据时，任何推导都不能保证绝对正确 |
| 数据严重异常时系统会怎样？ | **保守少画，不覆盖陆地** | 这是为纽约类风险设置的故障安全策略 |

因此，更准确的说法是：**本次根治了应用自身对复杂海岸线处理的结构性缺陷；没有、也不应假装根治上游开放地理数据的全部不确定性。**

如果未来允许引入全球权威海陆面数据，可以提高对严重缺口或错误方向数据的兜底能力。但那是提高数据上限的下一阶段，不是本次 V2 尚未补完的同一件事。

## 8. 以后遇到类似问题，应该怎样少走弯路

这次最重要的收获不是某个地理库的用法，而是处理此类问题的顺序：

1. **先定位失效层。** 先区分数据语义、几何推导、缓存/线程、绘制和导出，不从截图直接跳到修改颜色或顺序。
2. **先把用户案例变成可离线重放的最小样本。** 没有稳定复现，任何“修好了”都可能只是缓存、网络或偶然数据差异。
3. **用输出分辨率定义性能预算。** 不能把原始数据复杂度原封不动带进海报；也不能用一个脱离画面尺寸的固定阈值决定成败。
4. **用关系判断关系。** 海陆属于边与区域的邻接问题，不应由边旁边一个采样点来猜。
5. **让局部错误局部化。** 一处数据碎片不能抹掉整个城市可信的海面；同时，局部不确定不能被“猜对了”而扩大成陆地覆盖。
6. **把运行版本和最终输出纳入验收。** 单元测试证明算法，真实导出证明产品；两者缺一不可。

## 结语

水体渲染之所以反复，不是因为团队连续忽略同一个显眼 bug，而是因为每个城市都暴露了旧方案一个尚未被看见的前提。前几轮修复解决了真实问题，却没有及时把它们归纳为同一条数据处理链上的系统性约束。

这次 V2 的价值，在于不再试图为纽约、南京、海口或里斯本分别寻找例外，而是重新定义了海面生成应该依赖什么证据、如何控制成本、以及在不确定时如何安全失败。它让“蓝色是否出现”从一次视觉碰巧，变成了可追溯、可测试、可复核的工程结果。
